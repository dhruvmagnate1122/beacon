# Beacon brand guide

## Positioning

**Name:** Beacon  
**Category:** evidence-driven launch-readiness framework for web apps  
**Tagline:** **Evidence-driven launch readiness for web apps.**  
**Supporting line:** Catch privacy, regulatory, security, and operational gaps before launch — without pretending a scan is certification.

Beacon is developer-first. The product should feel like an engineering readiness system that can incorporate legal/regulatory evidence, not a law firm, audit certificate, or generic compliance checklist.

## Core promise

Beacon helps a team answer:

- What did we actually check?
- Which jurisdiction or operational rules are relevant?
- What evidence supports each result?
- What is still unknown?
- What is future-effective rather than presently in force?
- What needs human/legal/provider review before launch?

## Language

Prefer:

- launch readiness
- evidence-driven
- source candidate
- applicability
- readiness check
- runtime/config evidence
- primary-source-backed pack
- unknown / review required
- future-effective
- verify before launch

Avoid:

- compliant / non-compliant as a blanket product verdict
- certification
- approved / cleared
- guaranteed secure
- legally safe
- audit passed
- worldwide compliance
- automatic legal advice
- fine calculator

## Product architecture language

Use **pack** for executable legal/regulatory modules:

- India DPDP
- EU/EEA GDPR + ePrivacy
- UK GDPR + PECR
- US federal digital
- India CERT-In
- EU digital VAT / OSS

Use **operational check** or **adapter** for database isolation, cost controls, subscriptions, email suppression, accessibility testing, provider configuration, and similar non-jurisdiction modules.

Do not call provider or technical modules “jurisdictions.”

## Pairing with Litmus

- **Litmus** — product quality gate: security signals, technical SEO/discoverability, performance, conversion copy.
- **Beacon** — launch readiness: privacy/regulatory applicability, evidence, operational controls, subscriptions/accessibility/cost/data handling.

The projects can complement each other, but their status vocabularies and evidence semantics should not leak into each other.
